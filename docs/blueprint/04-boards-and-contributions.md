# 04: Boards and contributions

Status: board loading and optional skills built. The audit candidate supplies Moonlander and Glove80 guidance; it is not yet released and adds no firmware capability.

BK supports his own boards, and anyone with another board adds it (D-008). A board is data that keyloom can validate, plus an optional skill for the agent (D-009). Adding a board must never mean writing another configurator. There's no plugin system or marketplace: a board is a folder in this repo, added by pull request.

## A board is a folder

```
boards/
  zsa/moonlander/
    board.json         facts keyloom validates and uses
    geometry.json      generated from the pinned firmware tree; never edited by hand
    SKILL.md           optional agent guidance
  moergo/glove80/
    board.json
    geometry.json
    SKILL.md
  _template/           the folders a contributor copies; never a board (D-051)
    qmk/board.json
    zmk/board.json
```

The board ID is the folder path: `zsa/moonlander`, `moergo/glove80`. That's the same `<vendor>/<board>` shape QMK uses.

## `board.json`

```jsonc
{
  "schemaVersion": 1,
  "id": "moergo/glove80",
  "name": "Glove80",
  "vendor": "MoErgo",
  "firmware": "zmk",                                 // D-002
  "keyCount": 80,
  "revisions": [                                     // one entry when there's only one
    {
      "id": "default",
      "source": {                                    // the pinned firmware tree (D-036, D-040)
        "repo": "https://github.com/moergo-sc/zmk",
        "ref": "v26.09",
        "sha": "ce69e85f585c724142aae37ddf8a7e019ff19e93"
      },
      "build": {
        "kind": "zmk-moergo-template",               // a recipe keyloom implements (below)
        "template": { "repo": "https://github.com/moergo-sc/glove80-zmk-config",
                      "sha": "34888be8c9d9a3d5b168a502b8b191ba43b4a1f3" }
      },
      "flash": {
        "kind": "uf2-drives",
        "steps": [
          { "volume": "GLV80RHBOOT", "label": "right half",
            "enter": "With the right half off and USB connected, hold I + PgDn and switch it on. A slow red pulse means it's ready." },
          { "volume": "GLV80LHBOOT", "label": "left half",
            "enter": "With the left half off and USB connected, hold Magic + E and switch it on." }
        ]
      },
      "detect": null                                 // or { "usbProductId": "0x1969" } (Moonlander rev A, 05)
    }
  ],
  "hands": { "left": [0, 1, 2 /* … */], "right": [/* … */] },
  "fingers": { "0": "left-pinky" /* … every position */ },
  "rows": { "home": [/* positions */], "top": [/* … */], "thumb": [/* … */] },
  "mirror": { "0": 9 /* left position → right position */ },
  "importers": ["zmk-layout-editor-keymap"]
}
```

Fields keyloom checks (`keyloom boards check`, [10](10-cli.md)):

- **`firmware`** is `qmk`, `zmk` or `kanata`. It decides the importer, generator and validator rules; [21](21-macbook-keyboard.md) covers the software-remapper recipes.
- **`keyCount`** equals the number of keys in `geometry.json`, and every position from `0` to `keyCount - 1` appears in exactly one hand, one finger and one row group.
- **`revisions[].source`** names a repo and a full SHA. A `ref` is informational; the SHA is what's checked out ([01](01-architecture.md#firmware-toolchains)).
- **`build.kind` and `flash.kind`** are recipes keyloom implements, declared as strict schemas in `src/boards/recipes.ts` (D-049). A misspelled or unknown field is an error. Builds: `qmk-docker` for any QMK tree (mainline or a fork), `zmk-west-docker` for upstream ZMK with one `west build` per shield, and `zmk-moergo-template` for the Glove80. Flashes: `zapp` for ZSA boards, `uf2-drives` for UF2 boot drives (ZMK, and QMK on RP2040), `dfu-tool` for QMK boards whose bootloader a command-line tool writes (dfu-programmer, dfu-util, avrdude; D-365), and `manual` for boards keyloom can't flash yet (D-050). A board that needs a flasher or builder that doesn't exist needs code, and that is the one case a contribution is more than data.
- **`hands`, `fingers`, `rows` and `mirror`** feed the agent ([03](03-agent.md#what-the-agent-sees)), the validator's opposite-hand warning ([07](07-change-validation.md#warnings)), and "do that here too" mirroring (rung 7). They're the board facts the firmware doesn't carry. `mirror` lists each left-hand position once, with the right-hand key at the same height on the other half (D-060); `keyloom boards check` checks that each pair is one left and one right position; `test/boards/mirror.test.ts` holds every shipped board to the geometry, measured on the drawn, rotated centres, so thumb clusters count.

## `geometry.json` is generated from the firmware tree

The editor draws keys from `geometry.json`: one entry per position with `x`, `y`, `w`, `h`, `r`, `rx` and `ry` in key units. Positions follow the firmware's binding order. The file is generated by `keyloom boards geometry <board>` from the pinned firmware tree (D-045):

- **QMK:** the board's `keyboard.json` `layouts.<LAYOUT>.layout` (`x`, `y`, `w`, `h`, `r`, `rx`, `ry`) at the pinned fork SHA.
- **ZMK:** the `zmk,physical-layout` node's `keys` (`<&key_physical_attrs w h x y r rx ry>`, in hundredths of a key and of a degree), divided by 100.

`boards check` regenerates it and fails if it differs from the committed file. keymap-editor reads geometry from a separate `info.json` and community metadata. Its author's own issues show that drifting from the firmware and producing off-by-one layouts ([../research/keymap-editor.md](../research/keymap-editor.md)). The template's `info.json` beside MoErgo's Glove80 config is the same kind of file, and nothing reads it ([../research/zmk-and-glove80.md](../research/zmk-and-glove80.md)).

**Lighting and setting defaults.** A board with per-key RGB declares `"lighting": { "ledPositions": [...] }`, LED number to key position, read from the firmware's `rgb_matrix.layout` and keyboard layout by matching matrix coordinates (D-190). A board without it may say why in `"limits": { "lighting": "..." }`, one sentence the agent and the validator quote when someone asks for colours it can't show (D-224). `"settingDefaults": { "MOUSEKEY_ENABLE": true }` records where the board differs from the firmware's own default on the settings page (D-191).

**Display-only overrides.** The firmware's geometry is the source for positions and sizes, and it is not always the source for how the board looks. The Moonlander's `keyboard.json` doesn't tilt the thumb cluster and puts its two red keys on the bottom row. `board.json` may carry `"display": { "rotate": [{ "positions": [...], "r": 30, "rx": …, "ry": … }], "shift": [{ "positions": [...], "dx": 2 }], "keycaps": { "59": "red" } }` so the picture looks like the real board. `rotate` and `shift` apply only when drawing, in that order. `keycaps` names a physical keycap colour that the editor draws as a rim and a faint tint on that key (D-252). Generation, positions and the agent's grid ignore all three. `boards check` fails a position past `keyCount`, and `test/boards/display-overrides.test.ts` ties the Moonlander's overrides to the generated geometry's key sizes (D-251), so a regenerated `keyboard.json` that moves the keys fails there instead of drawing a stray cluster.

## `SKILL.md` is optional agent guidance

A board skill is Markdown that keyloom adds to the agent's context for that board ([03](03-agent.md#what-the-agent-sees)). It holds quirks and conventions: firmware limits, how a vendor default is organised, or owner-reported preferences. Cite the firmware evidence for technical guidance; comfort claims and personal habits must come from the owner, never a guess. BK's word was "skill", and this is it (D-009).

The candidate includes [Moonlander guidance](../../boards/zsa/moonlander/SKILL.md) and [Glove80 guidance](../../boards/moergo/glove80/SKILL.md), grounded in the pinned-firmware research and validation rules. They distinguish vendor defaults from imported bindings and physical LEDs from on-screen colours. `src/boards/load.ts` loads the optional file, and the bundled board registry embeds it; no plugin or mandatory per-board code is needed.

It's limited to 400 lines. `boards check` warns past that, because every agent turn pays for it ([12](12-cost-model.md)).

## Contributing a board

`CONTRIBUTING.md` (rung 8) walks a contributor through the steps below. It is the guide; this section is the outline. The guide's `board.json` field reference is checked against the zod schema by a test, so it can't drift.

1. Find the firmware tree that builds the board and pin a SHA.
2. Write `board.json`, choosing existing build and flash recipes.
3. Run `keyloom boards geometry <board>` to generate `geometry.json`.
4. Fill in `hands`, `fingers`, `rows` and `mirror` with the editor's position overlay (`keyloom serve --board-dev <board>` shows position numbers on each key, and what `board.json` says about the key under the pointer; it reads the folder afresh, so it works on an unfinished one).
5. Optionally write `SKILL.md`.
6. Run `keyloom boards check boards/<vendor>/<board>`, then import a real layout, build it, and flash their own board.
7. Open a PR with the folder. CI runs `boards check` on every board, fetching each pinned firmware file (cached by SHA) to compare geometry.

BK reviews board PRs for format only. He can't test hardware he doesn't own, so the PR description must say the contributor built and flashed it, with the keyloom version used.
