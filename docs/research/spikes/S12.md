# S12: the `keyloom-zmk` module on BK's Glove80

**Status (2026-10-17): partly run. The result is at the end: both Glove80 halves restarted into their bootloaders by themselves and one flash of both halves was verified. The Corne (S13), the relay on battery and two fault-free flashes in a row were not observed.**

Runbook for the orchestrator to run with BK. Written 2026-10-15 on branch `rung12/zmk-handsfree`; when it was written, nothing in it had been run on hardware. Everything that can be proven without the keyboards is in `evidence/rung12/` (three firmware builds with the module, the host code against fakes).

It settles three of the questions in [15-open-questions.md](../../blueprint/15-open-questions.md):

1. Does each Glove80 half, built with the module at `moergo-sc/zmk@ce69e85`, show a USB serial port carrying `keyloom/<12>-<L|R>:GLV80-<chip ID>`, and restart into its bootloader when the port is closed at 1200 baud?
2. Does the 1201-baud relay put the right half in its bootloader, and does a right half on battery return to typing after 3 s?
3. Does `keyloom flash` update both halves with no keypress, twice in a row?

Typing, Bluetooth and the settings kept across a flash are checked on the way (step 5), because a CDC interface that breaks the keyboard stops everything else.

## Before touching the keyboard

**Recovery.** Every step below can leave a half in its bootloader, which does not type. The key combos work whatever firmware is on the half, because the bootloader reads the matrix before it starts the app (`bl-moergo@bb68c75` `src/main.c:197-209`):

| Half | Hold, then switch the half on | Drive that appears |
|---|---|---|
| Right | I + PgDn, with its USB cable connected | `GLV80RHBOOT` |
| Left | Magic + E, with its USB cable connected | `GLV80LHBOOT` |

**Keep what is on the halves now.** MoErgo's bootloader is Adafruit's, which also serves `CURRENT.UF2`, a dump of the flashed firmware, on the boot drive. Do this once per half before anything is flashed, so the keyboard can be put back exactly as it was:

```
# put the right half in its bootloader (table above), then:
ls /Volumes/GLV80RHBOOT          # expect INFO_UF2.TXT, INDEX.HTM and, usually, CURRENT.UF2
cat /Volumes/GLV80RHBOOT/INFO_UF2.TXT
mkdir -p ~/glove80-backup && cp /Volumes/GLV80RHBOOT/CURRENT.UF2 ~/glove80-backup/right-current.uf2
# the drive stays until the half is power-cycled; switch it off and on, then the same for the left half with GLV80LHBOOT
```

Expected: `INFO_UF2.TXT` names a MoErgo Adafruit bootloader and a board such as `Glove80 v1 Right Hand`. If it says something else than `bb68c75`'s family, record it: the `0x57` GPREGRET path is old Adafruit code and very likely matches, but the file settles it. If `CURRENT.UF2` is missing, the fallback is MoErgo's own firmware from the Layout Editor, downloaded now and kept next to the backup. Writing the dump back is a copy of the file onto the same drive.

Do not run `keyloom flash --reboot-only`: it is QMK-only.

## 1. Build with the module (no hardware)

```
KL="bun /Users/bhekanik/code/planetaryescape/.worktrees/keyloom-r12/src/cli/main.ts"
$KL layout list                                   # pick BK's Glove80 layout
$KL build <layout> --format json                  # prints build_id and artifact_path
```

Expected: the build log (`log_path` in the output) contains `keyloom: the firmware carries keyloom's hands-free module (build key <12>)`. It takes about 30 s with the image present. That line is the check: it reads the UF2's payload in order, because the serial template can straddle two blocks and `strings` on the raw file then misses it (in the rung's Glove80 build, a raw search found 3 of the 4 templates and the joined payload found all 4).

If the log says `warning: the firmware does not carry the build key`, stop: the module did not get in, and nothing below will work. Send `<checkout>/config/default.nix` and the log to the author.

## 2. The first flash, by key combo

```
$KL flash --layout <layout> --format json
```

keyloom prints its instructions on stderr. Expected, in order:

1. `keyloom is checking whether it can restart the keyboard's halves into their bootloaders itself.`
2. `keyloom couldn't restart the right half by itself: no keyloom serial port was found for it, so it needs its bootloader key this once. Flash the right half (1 of 2). ... hold I + PgDn and switch it on ...`

Do the right half's combo. Then `Don't unplug or switch off the half. Writing takes a few seconds...`, then `The right half is restarting. Don't unplug it; keyloom is checking it came back.` Then the same two messages for the left half with Magic + E.

macOS may ask once to let the terminal write to a removable volume. Allow it; keyloom's error names the setting if it is refused.

Expected result (stdout, JSON `note`): `Verified: the right half is running build bld_..., and the left half is running build bld_....`

**Pass:** status `succeeded` and that note. **Fail, and what it tells you:**

| Seen | Meaning | Do |
|---|---|---|
| `didn't come back within 45 seconds` for the right half | No serial port after the flash. Either the half did not boot the new firmware, or the CDC interface is missing | `ioreg -p IOUSB -r -n "Glove80 Right" -l -w0 \| grep -E "USB Serial Number\|bInterface"` and save it. If the half types but has no port, S12 fails at "adds a serial port": keep the output and go to recovery |
| `came back with moergo.com:GLV80-...` | The old firmware is still on the half | The write did not take. Repeat that half once; if it repeats, record the drive's `INFO_UF2.TXT` and stop |
| The half does not type at all | App did not start | Hold the half's combo, copy the backup `.uf2` onto the drive |

## 3. After the first flash: what the host sees

```
ls /dev/cu.usbmodem*                      # expect two ports
ioreg -p IOUSB -r -n "Glove80 Left"  -l -w0 | grep -E "USB Serial Number|IOCalloutDevice|idProduct"
ioreg -p IOUSB -r -n "Glove80 Right" -l -w0 | grep -E "USB Serial Number|IOCalloutDevice|idProduct"
system_profiler SPUSBHostDataType | grep -A12 -E "Glove80 (Left|Right)"
```

Expected:

- Left serial `keyloom/<12>-L:GLV80-737753DA283F2ECA`, right `keyloom/<12>-R:GLV80-58291CCA4B6E75B0`. The last 16 characters are the chip IDs seen before the flash (`ioreg` on 2026-10-15), so they must not change.
- Each half's `IOCalloutDevice` is a `/dev/cu.usbmodem...` node. Note which is which: the left is the central.
- Product IDs still `0x27db` (left) and `0x27d9` (right).
- Before this flash the right half had zero USB interfaces. Record how many each half has now: the right half is the unproven case, because it ran with `CONFIG_ZMK_USB=n`.

```
$KL doctor --format table | grep -i glove
```

Expected: two lines, `keyboard moergo/glove80 left half: running keyloom build <12> (serial port /dev/cu.usbmodem...); the next flash needs no keypress`, and the same for the right half.

## 4. Typing, Bluetooth and settings (do before going on)

- Type on both halves over USB for a minute: all keys, a layer key, a hold-tap. Compare against the layout.
- Unplug both cables, switch Bluetooth on, pick the Glove80's slot the Mac is paired to, and type on both halves. **Expect:** it reconnects without re-pairing. If it does not, remove the pairing in System Settings, pair again, and record that a flash lost the bond.
- Leave the cables in for steps 5 and 6.

## 5. Two hands-free flashes

Make the second build differ from the first, so verification means something. Any change does; a new build ID is enough, so rebuilding the same layout is fine:

```
$KL build <layout> --format json
time $KL flash --layout <layout> --format json
```

Hands in the lap. Expected on stderr:

1. `keyloom is checking whether it can restart ...`
2. `keyloom is restarting the right half into its bootloader. Don't touch the keyboard.` (the right half stops typing)
3. `Don't unplug or switch off the half. Writing takes a few seconds, ...`
4. `The right half is restarting. Don't unplug it; keyloom is checking it came back.`
5. The same for the left half. The keyboard stops typing for a few seconds there, since the left half is the central.

The flash log (`log_path`) must show, per half, the line `closing /dev/cu.usbmodem... at 1200 baud restarts it into its bootloader` and `GLV80RHBOOT appeared; the right half is in its bootloader` (then LH). No `couldn't restart` line. Record the elapsed time and how long the right half and the left half were out.

**Pass:** `succeeded` with `Verified: ... build bld_<the new one>`; the serials in step 3's `ioreg` now carry the new key; typing works. **Run it a second time** (third build): a latch or a stale port would show here.

| Seen | Meaning | Do |
|---|---|---|
| `GLV80RHBOOT didn't appear within 15 seconds of restarting the right half` and the key combo is asked for | The touch reached the half but it did not enter UF2 mode, or the drive is slow to mount | `stty` is not the problem if the half's LED changed. Run the touch by hand (step 6) and watch the half |
| `stty could not set /dev/cu.usbmodem... to 1200 baud: ...` | stty refused or no permission | Record the text. On macOS nothing but a missing device should fail |
| The flash stops with `came back with ...` | Verified failure; the next half was not touched | `ioreg` the half, then recover as in step 2 |

## 6. The relay, and a right half on battery

Find the left half's port (step 3) and set `LEFT=/dev/cu.usbmodem...` and `LEFT_SERIAL` accordingly. These commands are the spike's own; they are the only place `stty` is run by hand.

**6a. Relay with the right half on its cable.** The right half's own port exists, so this only tests the relay:

```
stty -f $LEFT 1201
sleep 4; ls /Volumes | grep GLV80
```

Expected: `GLV80RHBOOT` is listed, the right half stops typing, the left half keeps typing. If `stty` answers `Invalid argument`, record the text: macOS then cannot send 1201, and D-133's relay rate has to change (another standard rate, or a text command on the port).

Repeat `stty -f $LEFT 1201` after the half has been recovered: a second relay must work (it proves the firmware reset the rate to 115200 after the first). Recover the right half without flashing by switching it off and on, or with the next command.

**6b. A stranded half is accepted by `keyloom flash`.** With `GLV80RHBOOT` mounted:

```
$KL flash --layout <layout> --format json
```

Expected: the log has `GLV80RHBOOT is already mounted, so the right half is already in its bootloader`, the right half is written, then the left half is restarted by its port, and the result is verified.

**6c. The right half on battery.** Unplug the right half's USB cable, with the half switched on and typing over Bluetooth into a text field.

```
stty -f $LEFT 1201
```

Expected: the right half's keys stop for about 3 s (its bootloader gives up with no USB) and then type again; no `GLV80RHBOOT` appears in `/Volumes` at any point; the left half is unaffected. Time it with a key held down or a stopwatch. This confirms the relay is harmless with the cable out (`bl-moergo@bb68c75` `src/main.c:337-345`).

Then plug the cable back in and run 6a once more to confirm the cable is what mounts the drive.

**6d. The left half.** `stty -f $LEFT 1200` restarts the left half into `GLV80LHBOOT`; recover it with the next `keyloom flash` or a power cycle. Do this once by hand and note how long the drive takes to appear.

## 7. What to record

For the result section in 15-open-questions.md and `S12 result` here: the `INFO_UF2.TXT` of both halves; build IDs; the ioreg output of step 3; the number of USB interfaces per half; times from step 5 (twice); the outcomes of 6a to 6d; whether `stty` accepted 1201; whether Bluetooth re-paired; and anything in the flash log that was not in this runbook.

## Failure playbook

| Situation | Action |
|---|---|
| A half is in its bootloader and the Mac shows no drive | Unplug and replug its cable. If it still shows nothing, power-cycle it with the combo held |
| A half types wrong or not at all after a flash | Combo, then copy the backup `.uf2` (or MoErgo's firmware) to the drive |
| Both halves lost Bluetooth | Remove the Glove80 pairing in System Settings, re-pair; if the halves do not find each other, flash MoErgo's `settings_reset` firmware or use the Layout Editor's reset steps |
| The module breaks typing over USB (CDC and HID conflict) | Restore the backup on both halves and report the `ioreg` output; S12 then fails at "keyboard unchanged" and the descriptor needs work |
| `keyloom flash` is stuck waiting | It gives up after 2 minutes with the half's name; Ctrl-C cancels it and leaves the halves flashed so far |

Never flash from a spike with a build whose log lacks the `carries keyloom's hands-free module` line.

From the three hands-free runs:

- Five of five restarts into the bootloader worked at 1200 baud with no keypress: right, right and left, right and left. The drive named `GLV80RHBOOT` or `GLV80LHBOOT` appeared each time. Each half's serial port carried a `keyloom/<build key>-<L|R>` prefix before the flash, which answers the first question of this spike: the module is in the firmware and gives each half a serial port with keyloom's marker.
- Writes were refused with `EACCES` three times in five and worked on the retry (v0.34.3, `84d0b29`).
- The last run's timings, from `keyloom sync status`: 4.2 s waiting, 17.8 s build, 15.3 s flash for both halves, 37.3 s from Apply to verified.
- Both faults in the middle runs were false failures, not bad flashes. The second run's right half did run the new build: the third run found it reporting `CQPJ0WEFM8T7`. The third run's left half did too: the fourth run found it reporting `CQPJ0WEFM8T7` before it started.

Two bugs the runs exposed, both fixed the same night:

- The verify read a half that had come back on USB but not yet on its serial port as other firmware (`47de622`, released in v0.34.6). It matches the second run's failure. I did not replay that run against the fix.
- A device-gone write error was reported as a failed flash while macOS still listed the drive (`acbfa07`, v0.34.7). The commit message describes the left half taking the file and rebooting on the last block, which matches the third run.

State on 2026-10-17:

- `ioreg` shows `keyloom/BAFNJPGEVV5Y-R:GLV80-58291CCA4B6E75B0` for "Glove80 Right" and `keyloom/BAFNJPGEVV5Y-L:GLV80-737753DA283F2ECA` for "Glove80 Left". Both halves run the last build.
- `keyloom sync status` shows the Glove80 `in_sync` at head revision `rev_01M53ED88AHHFCYW00MCE7QD3T`, auto-sync on and proven. The last sync is `syn_01M53EDCC60RQPFKJ3KRQJ48MY`. This is the last build, `BAFNJPGEVV5Y`, not `CQPJ0WEFM8T7`, which was the build of the two failed attempts.

### What was not observed

- **Two hands-free flashes in a row with no fault.** After the fixes there is one complete flash. It had an `EACCES` retry on each half, handled by the retry. The two earlier hands-free runs ended in a false failure.
- **The 1201-baud relay and a right half on battery** (step 6). Every restart used the half's own port, so the relay was never needed. Whether `stty` accepts 1201 on macOS is unknown.
- **Typing, Bluetooth and settings kept across the flash** (step 5). The logs do not say. BK typed on the Glove80 after the earlier S8 flash, not recorded for these.
- **The backups** (`CURRENT.UF2`, `INFO_UF2.TXT`) and the `ioreg` interface count per half.
- **The build's "carries keyloom's hands-free module" line.** The three build logs do not contain it. The serial prefix on both halves shows the module is in the firmware.
- **The Corne** (S13) and MoErgo's tools (S18).

### Conclusion

The module builds into the MoErgo fork for both halves, gives each a serial port with keyloom's marker, and reboots each into its bootloader on a 1200 baud close. Hands-free flashing of both halves works and was verified once. The "done when" of rung 12, two clean hands-free flashes in a row on both ZMK boards, is not met: it needs one more fault-free Glove80 flash and the Corne.
