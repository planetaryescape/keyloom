# S16: Oryx tap dances into the model, and QMK against ZMK

Run 2026-10-15 on `rung14/tap-dance-macros` (from `fcc45ee`), with BK's real Moonlander export (`test/fixtures/oryx/synchronized`) and the pinned QMK checkout (`zsa/moonlander` reva) in Docker. Raw reports are in `.orchestrate/keyloom-2026-10-15/evidence/rung14/` (`qmk-oryx-vs-keyloom.json`, `qmk-esc-caps.json`, `qmk-macros.json`, `zmk-glove80.json`, `zmk-corne.json`, `zmk-macros-*.json`). Commands: `KEYLOOM_DOCKER_TESTS=qmk bun test test/firmware/qmk/tap-dance.docker.test.ts` and `KEYLOOM_DOCKER_TESTS=zmk bun test test/firmware/zmk/tap-dance.docker.test.ts`.

## 1. Can TD0, TD1 and DF0 be imported and regenerated with the same behaviour?

TD0 and TD1 import as tap dances: tap Hyper+Space with double-tap `[`, and tap Alt+Space with double-tap `]`. DF0 does not, on purpose.

- **Import.** `importOryxSource` reads both into `Layout.tapDances` and no tap dance code is left in passthrough (`test/firmware/qmk/import.test.ts`). Oryx's own GraphQL decoding of the two keys (tap, double-tap, no hold, no tap-hold) agrees with the model's slots (`test/helpers/oryx-oracle.ts`, compared key by key for all 432 keys).
- **Round trip.** import, generate, import gives an equal layout (`test/firmware/qmk/generate.test.ts`, `tap-dance.test.ts`). The importer only accepts code that keyloom's generator writes back identically (D-153).
- **Behaviour.** Ten key scripts (tap, double-tap, hold, tap then hold, triple and quadruple tap, tap or double-tap followed by another key, hold with another key pressed, tap then a tap after the term) were run for each of TD0 and TD1 on QMK's real core, once on Oryx's `keymap.c` as exported and once on keyloom's regenerated source. All 20 runs gave the same reports, timing included (`qmk-oryx-vs-keyloom.json`). The runs are not vacuous: a tap sends the Hyper chord after the 200 ms term, a double-tap sends `[`, a hold sends nothing (Oryx's code has no hold case), a triple tap sends the chord three times.
- **DF0 is `LT(5, KC_4)` plus a `process_record_user` case.** Tap sends F5. Hold calls `layer_move(5)` on press and on release, so the layer stays on. It has no double-tap, so it isn't a tap dance, and as a hold-tap it would be momentary, which leaves the layer on release. Both would be a plausible but wrong mapping, so it stays `native` with its code kept.
- **A found bug in the emulator, fixed.** The QMK harness counted elapsed time itself, so Oryx's `wait_ms(10)` in each dance reset pushed every later event late: the second dance's scripts ran 110 ms late. It now reads QMK's clock (D-158).

## 2. Does ZMK `&td` with generated hold-taps match QMK?

The keys typed agree for tap, double-tap, hold and tap-then-hold, on both the Glove80 and the Corne (their reports are identical). The feel differs in six ways. Rows are what each firmware sent, as `key@ms`; the script is shown by name. The other key in the "another key" rows is A on the Moonlander and U on the Glove80 and the Corne. QMK times are within 10 ms: each earlier dance in a run still adds its `wait_ms(10)`.

| Script | QMK | ZMK |
|---|---|---|
| esc-caps: tap | Esc@201 | Esc@201 |
| esc-caps: double-tap | Caps@321 | Caps@120 |
| esc-caps: hold | nothing | Esc@201 |
| esc-caps: tap then hold | nothing | Caps@120 |
| esc-caps: triple tap | Esc@240, Esc@240, Esc@240 | Caps@120, Esc@441 |
| esc-caps: quadruple tap | Esc@240, Esc@240, Esc@240, Esc@360 | Caps@120, Caps@360 |
| esc-caps: tap, then another key | Esc@100, A@110 | Esc@100, U@100 |
| esc-caps: double-tap, then another key | Esc@220, Esc@220, A@230 | Caps@120, U@220 |
| esc-caps: hold, another key pressed meanwhile | Esc@100, A@100 | Esc@100, U@100 |
| esc-caps: tap, wait out the term, tap again | Esc@201, Esc@711 | Esc@201, Esc@701 |
| all-slots: tap | Esc@211 | Esc@201 |
| all-slots: double-tap | Caps@321 | Caps@160 |
| all-slots: hold | Shift@211 | Shift@401 |
| all-slots: tap then hold | Tab@321 | Tab@321 |
| all-slots: triple tap | Esc@240, Esc@240, Esc@240 | Caps@160, Esc@441 |
| all-slots: quadruple tap | Esc@240, Esc@240, Esc@240, Esc@360 | Caps@160, Caps@400 |
| all-slots: tap, then another key | Esc@100, A@110 | Esc@100, U@100 |
| all-slots: double-tap, then another key | Esc@220, Esc@220, A@230 | Caps@160, U@220 |
| all-slots: hold, another key pressed meanwhile | Esc@100, A@100 | U@100, Esc@300 |
| all-slots: tap, wait out the term, tap again | Esc@201, Esc@711 | Esc@201, Esc@701 |

1. **Double-tap fires early on ZMK.** On the second press (Caps at 120 ms), or at its release when a tap-then-hold slot exists (160 ms). QMK waits out the term (321 ms).
2. **Three or more taps.** QMK types the tap that many times (Oryx's `on_dance_n` does that). ZMK cycles: the third tap starts a new dance (Caps, then Esc).
3. **A double-tap followed soon by another key.** QMK reads it as two taps and types Esc, Esc, A. ZMK types the double-tap action (Caps), then the key.
4. **An empty hold or tap-then-hold slot.** QMK does nothing while the key is held (no case in Oryx's code). ZMK holds the tap, or the double-tap, down while the key is held.
5. **Hold takes two terms on ZMK.** Shift at 401 ms against 211 ms. ZMK's tap dance presses its first binding when its own term ends, and the hold-tap in that position starts its own term then. A 10 ms hold-tap term fixed the timing but typed `U` then `Shift+U` when a key was pressed during the term, so it was not kept.
6. **Hold with another key pressed during the term.** QMK types Esc then the key. ZMK types the key first and the tap at release (the cause was not diagnosed).

Tap and tap-then-hold timings match within 10 ms (Esc at about 201 ms, Tab at 321 ms on both). ZMK has no per-key fallback term, so an unset `termMs` is written as 200 ms.

## 3. Macros

A three-step macro (Command-C, 100 ms, Command-Tab, 300 ms, Command-V) and a text step (`Thanks, "BK"!`) run on both. QMK sends the chords at 0, 100 and 400 ms and types the text exactly (`qmk-macros.json`). ZMK sends the same chords and text but not the waits: a `waitMs` step is written as `&macro_wait_time`, which sets the pause between the following bindings and gave 47 ms (docs/issues/zmk-macro-wait-is-not-a-pause.md). That predates this rung and is not fixed here.

## 4. What stays open

- Layouts stored before this change keep their Oryx tap dances native and can't gain tap dances until the layout is updated from the layout summary or with `keyloom layout upgrade` (D-193).
- A dance whose code isn't exactly what keyloom writes (a third step, another delay, extra cases in `get_tapping_term`) is not imported at all. No such file was available to try; the failure cases are tested with edits to BK's file.
- ZMK tap dance nodes are written, not read back.
