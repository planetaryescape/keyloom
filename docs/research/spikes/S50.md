# S50: the Moonlander's key stream on BK's keyboard

The build half is done; the hardware half is a runbook for the orchestrator with BK at the keyboard. Nothing below has run on a keyboard: keyloom's tests never open a real HID interface, and the worker that built this did not stream from BK's Moonlander.

## What is already proven (2026-10-16, no hardware)

- The firmware C compiles and behaves as specified when driven on the host: `test/firmware/qmk/typing-stream.test.ts` (off at power-up, batching, the position table, stop, the 10 minute limit, the quiet host, a blocked send, a stray start, the bootloader command still working).
- It builds beside Oryx's modules for both revisions with ZSA's pinned fork `93b2b9e` in the pinned image: reva 68,140 bytes (plain 67,268), revb 70,380. `buildQmk` refused the build unless the ELF defined `__wrap_action_exec`; `nm` and `objdump -d` show `matrix_task`'s two calls going to `__wrap_action_exec`, which tail-calls `action_exec`, and an 84-byte `keyloom_lab_position` table (12 rows by 7 columns). Log: `evidence/rung22/qmk-moonlander-build.log`, `moonlander-symbols.txt`.
- The host reader decodes the same reports against a fake keyboard (`test/firmware/toolchain/key-capture.test.ts`).

## What needs the keyboard

The macOS reading path (`hid-macos.ts` `openSession`, IOKit with a pumped run loop) is written from the headers and has not run. The questions are: does it receive the reports, does the keyboard keep up at fast typing without dropping events, does the stream stop by itself, and does typing feel the same while it runs.

Setup. Flash a hands-free build that has the stream: `keyloom sync <layout>` (this build; an older keyloom build has no stream and the probe will say so). macOS asks for Input Monitoring for the terminal the first time: allow it under System Settings, Privacy & Security.

### 1. It answers, and positions are right (2 minutes)

```sh
bun scripts/lab-probe.ts qmk --seconds 30
```

Prints `streaming from Moonlander`, then one line per event. Press the keys at the corners and the thumbs: key numbers are position plus one, as the editor shows them (the top-left key is 1, the red thumb key 67). Pass if every key you press is the number the editor shows for it, and a press and its release both appear.

### 2. Fast typing drops nothing (3 minutes)

Run the probe for 60 seconds and type as fast as you can for most of it, including rolls and both hands at once. The probe prints warnings at the end. Pass if there is no "never arrived" (a lost report) and no "dropped" (the keyboard's queue overflowed). The count of events printed should equal twice the keys you pressed; count a short burst by hand to check.

Also watch the keyboard: any added lag in the typed letters, or a key that sticks, is a failure even with no warning (the firmware stops the stream on a send that blocks 20 ms or more, which would be the cause).

### 3. It stops by itself (6 minutes)

a. Crashed host. `bun scripts/lab-probe.ts qmk --no-stop`. It exits without telling the keyboard. Wait 5 seconds, then run the probe again. Pass if it connects ("streaming from"): the first stream ended within 3 seconds. If it says the keyboard did not start streaming, the stream was still on.

b. Stalled host. Run `bun scripts/lab-probe.ts qmk --seconds 120`, then `kill -STOP <pid>` from another terminal, wait 6 seconds, `kill -CONT <pid>`. Pass if the probe then reports `ended by the host stopped answering`.

c. The limit. Run `bun scripts/lab-probe.ts qmk --seconds 700` and type a key now and then. Pass if it reports `ended by the 10 minute limit` at about 10:00, though the host kept answering.

d. Unplug and replug the keyboard during a run. Pass if the probe reports the connection failure (or the keyboard stopping) and the keyboard types normally when plugged back in, with no stream until asked.

### 4. Off by default

Reboot the keyboard (unplug and plug in) and type for a minute without running anything. Pass if typing is normal. Nothing is sent unless the host asks; this cannot be observed from the keyboard, so the check is that `lab-probe` printed nothing before its own start.

## Record

Write the result as "### S50 result" in `docs/blueprint/15-open-questions.md`: the four passes or failures, the fastest burst you managed (events per second), and any lag. If 2 fails with a dropped count, raise the ring (`KEYLOOM_LAB_RING` in `typing-stream.ts`) or lower the flush time and rebuild.
