# S42: does keyloom name BK's boards from USB alone?

## What was run

`keyloom keyboard detect` with an empty scratch data directory, on BK's Mac.

- 2026-10-16 (rung 21 part 1, `bb86f07`): recorded in [15-open-questions.md](../../blueprint/15-open-questions.md) under "S40 and S42 results".
- 2026-10-17, re-run for this file, on the branch of this change:

```
Glove80 Right  0x16c0:0x27d9  v0x0305  MoErgo
  your Glove80 (moergo/glove80)

Glove80 Left  0x16c0:0x27db  v0x0305  MoErgo
  your Glove80 (moergo/glove80)
```

## What was observed

- **Glove80:** both halves are named from USB alone and matched to the board keyloom already has, so detection stops there. `0x16c0:0x27db` is also one of the 11 V-USB IDs QMK boards share, which is why candidates that only share an ID are dropped once one fits.
- **Moonlander:** not plugged in during either run. By the committed index alone, `0x3297:0x1969` names `zsa/moonlander` uniquely (a test, not a reading from his board). `0x1972` is a ZSA fork ID that upstream QMK's data does not list, so keyloom would recognise it through the board definition's `detect`, not the index. That is a statement about the code. It is not a reading of BK's Moonlander, and it says nothing about which revision he owns (see [S1](S1.md)).
- **Corne:** not plugged in. With a fake bus, a `Corne` product string over ZMK's default ID gives `zmk:corne` at 80%. The right half's product string is unobserved.
- **What it asks when it cannot decide:** a ranked list of candidates with the reason each fits; `unknown` with `--search` for a ZMK keyboard whose string names nothing; and for a shared or placeholder ID a list that is never reduced to one.
