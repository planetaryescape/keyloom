# S59: macOS native HID and serial on real keyboards

Run on 2026-10-22, 02:20–03:40 BST, on BK's MacBook (arm64, Darwin 27.0.0). BK authorized the run, and separately one Moonlander flash, in the same session. The recordings used scratch data directories and a public passage, "the quick brown fox jumps over the lazy dog". Only counts, status and warnings were read. The recordings were not kept.

The arm64 HID and serial halves pass for capture, stop, restart, helper death, unplug and reopen, once the three fixes below are in. Defaults stay unchanged: Intel, the minimum macOS version, the web lab path, `serial.touch` and the signed release helper were not covered.

## Builds

Candidates came from `bun scripts/build-binaries.ts --target bun-darwin-arm64 --device-backend native-serial|native-hid --out-dir <separate dir>`. Each helper was compiled from source and ad-hoc signed.

- Before the fixes: tag `v0.48.0` (`1ac81332864d150e086f0cb5f51bb3db01fdee54`). Serial helper sha256 `3f86d151…`, HID helper `66c62173…`.
- After the fixes: branch `fix/serial-identity-usb-device`. Serial helper `cf15ce24…` at `4ef4745`, HID helper `0dc8149a…` at `3a8bbd2`.

## Glove80 with the keyloom-zmk module (native-serial)

The board is a MoErgo Glove80 with VID `0x16c0`. The left half is PID `0x27db`, the right `0x27d9`. The serial numbers are `keyloom/<build>-L:GLV80-<id>` and `…-R:…`. Each half's CDC data port is on interface 1.

### Bug 1: discovery listed both halves without their serial numbers

The legacy 0.48.0 and 0.46.1 builds found both halves. The native candidate's `list {transport:"serial"}` returned both endpoints with VID/PID but no `serial`, `product` or `interfaceNumber`, so `lab start` reported "no Glove80 running keyloom's firmware is connected".

`ioreg` showed the cause. The chain under the callout device is `IOSerialBSDClient` ← `AppleUSBACMData` ← `IOUSBHostInterface@1` ← `IOUSBHostDevice`. macOS copies `idVendor`/`idProduct` onto `AppleUSBACMData` and both interfaces, but `AppleUSBACMData` has no `USB Serial Number`. The backend took identity from the first ancestor with both IDs, so it read the data node.

The fix (`4ef4745`) takes identity from the nearest ancestor that conforms to `IOUSBHostDevice` or `IOUSBDevice`. Afterwards the list showed `serial`, `product` and `interfaceNumber: 1` for both halves. A regression test models the observed chain.

### Serial results

| Run | Result |
|---|---|
| Normal capture | 90 key events, complete, analysable. Its only warning was the Ctrl key still down at Ctrl-C |
| Helper `SIGKILL` 8 s in | Saved incomplete: `Recording incomplete: … keyboard connection: helper_exited`. Analysis exits 2. Helper and CLI both exited |

| Left half unplugged, after the fix | Saved incomplete: `… keyboard connection: disconnected` |
| Reopen after replug | Capture started normally |

Neither half restarted, entered its bootloader or stopped typing during any open or close. Several opens closed at 115200 with DTR cleared.

### Bug 2: unplug was reported as the helper exiting

Temporary close-step logging showed that after the unplug, the read failed `disconnected`. `TIOCCDTR` and `TIOCNXCL` then failed with `ENXIO` (6), while `close()` succeeded. The checked close returned `io_failed`, so the owner exited the process to keep the lease, by design for unconfirmed cleanup.

The fix (`4ef4745`, D-432) treats `ENXIO` from line control as nothing left to clear. Review round 2 dropped `ENODEV`: on Darwin it means "operation not supported", not removal. The fd release still decides the close. Any other line-control failure still fails it.

## Moonlander Mark I (native-hid)

The board is VID `0x3297`, PID `0x1969` (rev A), serial `keyloom/<build>`. This settles the S1/S42 rev conflict in favour of rev A.

### The firmware predated the typing lab

Both the legacy 0.48.0 build and the native candidate stopped with "the keyboard didn't start streaming". The native path still showed list, open, write of the start command, and a clean close with no helper left behind.

With BK's authorization, installed keyloom 0.46.1 ran `keyloom sync run <BK's Moonlander layout>`. The result was `synced`: build 167 s, hands-free flash 24 s, verified running.

### HID results

| Run | Result |
|---|---|
| Normal capture | 114 key events, complete, analysable |
| Helper `SIGKILL` 8 s in | Saved incomplete with `helper_exited`. Analysis exits 2 |
| USB unplugged mid-line, before the fix | Saved incomplete, but blamed `helper_exited` (bug 3) |
| USB unplugged, after the fix | Saved incomplete: `… keyboard connection: disconnected` |
| Reopen after replug | Capture started normally |

### Bug 3: unplug was reported as the helper exiting

Temporary logging showed that the removal callback had set `disconnected`, and then `IOHIDDeviceClose` returned `0xe00002c2` (`kIOReturnBadArgument`). The checked close failed, and the owner exited.

The fix (`3a8bbd2`, D-432) treats `kIOReturnBadArgument`, `kIOReturnNoDevice` and `kIOReturnNotAttached` as a clean close, but only after the removal callback has fired.

## Not observed

- Intel Macs and any macOS other than Darwin 27.0.0.
- The web lab and desktop app paths. Only the CLI was run.
- The notarised release helper. The candidates were ad-hoc signed local builds.
- `serial.touch` (1200 local and 1201 relay), which is unsupported.
- Parent (CLI) death, a stuck read, permission refusal, and CPU/RSS comparison with the legacy backend.
- Unplugging the right Glove80 half, and Bluetooth fallback.
