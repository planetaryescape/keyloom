# S8: the combined UF2 on both halves

## Static facts, 2026-10-15

Built with keyloom's Docker route from the template's default keymap at `moergo-sc/zmk@ce69e85f` (`v26.09`): `glove80.uf2`, 819,200 bytes, sha256 `db01ed58493c669df7615af1042f4ba666b258441db8ad64f20a2993a96291fc` (keyloom's generated source, header revision `rev_TEST`; the bytes depend on that header, so another run gives another hash).

It is 1,600 UF2 blocks, two images end to end:

| Image | Family ID | Blocks | Target addresses |
|---|---|---|---|
| first (the left half's `zmk.uf2`, built first by `combine_uf2 glove80_left glove80_right`) | `0x9807b007` | 894 | `0x00026000`..`0x0005de00` |
| second | `0x9808b007` | 706 | `0x00026000`..`0x00052200` |

Both images target the same addresses, and each block carries the family-ID flag. A UF2 bootloader that honours the family ID writes only the blocks that name its own, so each half skips the other's image. That is how the format works; it is not something this spike observed a Glove80 bootloader do. Which family belongs to which half is also not read from the file: the order of the images follows the order of the `cat`, so the first is presumably the left.

keyloom refuses to flash a file that isn't exactly two images with different family IDs (`uf2Problem`, `src/firmware/zmk/uf2.ts`).

## Result: both halves took the file and booted (2026-10-15)

**What was run.** `keyloom flash --wait 15` (v0.10.1) of build `bld_01M4ZXEWMANN3V3H25Y28EC6JP`, keyloom's build of BK's `42-key-map` keymap (two images, family `0x9807b007` 930 blocks and `0x9808b007` 706 blocks, the same layout of blocks as above). Flash `fl_01M5067Z2Y2JT3EDYD3JCY0NSC`, 16:27:36 to 16:28:17Z. BK put each half in its bootloader with the key combo when asked.

**What was observed.**

- The flash log shows `GLV80RHBOOT` mounted, written and unmounted, then `GLV80LHBOOT` mounted, written and unmounted, then `right half and left half flashed`. Status `succeeded`.
- Each bootloader took its own image: the right half first, then the left.
- Both halves came back on USB as "Glove80 Right" and "Glove80 Left", and BK typed on the board. Recorded in the build ledger, not re-checked: his words, "typing works as you can see."

**Failed attempts before it.**

- About 15:00Z, same build: the right half never entered its bootloader in 900 s, nothing was flashed. Recorded in the build ledger, not re-checked.
- `fl_01M5066BDXSVVD2CF3ZJT0JMN5`: `EACCES` on writing `glove80.uf2` to `GLV80RHBOOT`. The agent's sandbox blocks writes to `/Volumes`. `190dd57` made keyloom explain the error, since macOS raises it for an app without Removable Volumes access.

**What is still open.** Whether a bootloader rejects, instead of skips, the other half's blocks was not tested separately: the one flash worked. The flash shows that each half ended up running, not how the other half's blocks were handled.
