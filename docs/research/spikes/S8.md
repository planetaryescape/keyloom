# S8: the combined UF2 on both halves

## Static facts, 2026-10-15

Built with keyloom's Docker route from the template's default keymap at `moergo-sc/zmk@ce69e85f` (`v26.09`): `glove80.uf2`, 819,200 bytes, sha256 `db01ed58493c669df7615af1042f4ba666b258441db8ad64f20a2993a96291fc` (keyloom's generated source, header revision `rev_TEST`; the bytes depend on that header, so another run gives another hash).

It is 1,600 UF2 blocks, two images end to end:

| Image | Family ID | Blocks | Target addresses |
|---|---|---|---|
| first (the left half's `zmk.uf2`, built first by `combine_uf2 glove80_left glove80_right`) | `0x9807b007` | 894 | `0x00026000`..`0x0005de00` |
| second | `0x9808b007` | 706 | `0x00026000`..`0x00052200` |

Both images target the same addresses, and each block carries the family-ID flag. A UF2 bootloader that honours the family ID writes only the blocks that name its own, so each half skips the other's image. That is how the format works; it is not something this spike observed a Glove80 bootloader do. Which family belongs to which half is also not read from the file: the order of the images follows the order of the `cat`, so the first is presumably the left.

keyloom refuses to flash a file that isn't exactly two images with different family IDs (`uf2Problem`, `src/firmware/zmk/uf2.ts`).

## Not run

Nothing was copied to a keyboard. Whether both halves boot from the combined file, and the exact behaviour of each bootloader when it meets the other half's blocks (it may reject the file instead of skipping, or write the first image it sees), needs BK's Glove80. The flash code treats the drive unmounting as success and a drive that stays mounted as failure, which covers either behaviour but does not tell them apart.
