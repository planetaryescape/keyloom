# S33: kanata's simulator against keyloom's QMK emulator

Run 2026-10-17 and 2026-10-18. 15 home-row-mod scenarios and 10 QMK option sets, the same key events through both. 150 pairs: 144 agree and 6 differ, all from two kanata semantics (below). One translation bug was found and fixed (QMK `CHORDAL_HOLD` on its own). No keyboard was involved at any point.

## What was run

kanata 1.12.0 is installed (`kanata --version`). The v1.12.0 macOS release has no `kanata_simulated_input`, so it was built from the tag: `jtroo/kanata` `v1.12.0` is `02242ef761ef43b860eac30067ce86904be7d466`, crate `simulated_input/` (`kanata-sim`, default features `simulated_output` and `tcp_server`). Build, with rustc 1.98.0, in 39 s:

```
cd ~/.cache/keyloom-s33/src/simulated_input
CARGO_TARGET_DIR=~/.cache/keyloom-s33/target agent-work run -- cargo build --release -j 4
```

The binary is 1,955,104 bytes, sha256 `1b07ed5f...`, at `~/.cache/keyloom-s33/target/release/kanata_simulated_input`, outside the repo. It reads `-c config.kbd -s script.txt` and prints what kanata would output; it never opens a keyboard. The running kanata service and its port 5829 were not touched.

The QMK side is `keyloom emulate`'s own path (`emulateQmk`): BK's Moonlander layout generated to `keymap.c` and run on QMK's real core in Docker, at the pinned checkout `93b2b9ec3368f86c5eb5a2e3f934049f8daef885`. The kanata side is the MacBook layout keyloom generates for the same options: the QMK profile goes through `translateHoldTapProfile`, then `generateKanataSource`. So the test covers the translation table, not just kanata.

Both sides get the eight home keys (A S D F as Command, Option, Control, Shift; J K L as right Shift, Control, Option) as hold-taps, with the tapping term 200 ms, and the same scenarios. The scenarios and option sets are in `test/helpers/hrm-differential.ts`; each scenario starts 2 s after the last so none leaks into the next.

Two choices that bear on the numbers. BK's Moonlander has combos on S and D, and QMK holds a combo key back for `COMBO_TERM` (50 ms) in case the other half follows. The first run showed every tap QMK decided at the press arriving exactly 51 ms later than kanata's; with the layout's combos removed for this test the 51 ms disappeared in every case, so it was the combos and not hold-tap behaviour. And "matches" below means the same HID reports in the same order with each report within 10 ms; kanata's output lags its own decisions by about 6 ms.

## Where they differ

1. **`QUICK_TAP_TERM` counts from different moments.** QMK compares the new press with the first tap's last event, the release (`quantum/action_tapping.c#L26` and `#L572` at `93b2b9e`). kanata's `tap-repress-ms` is set when the first press enters the hold decision and counts down from there (`keyberon/src/layout.rs#L2054` and `tick_lpt` at `#L1188`, `02242ef`). With a window of 120 ms, a second press 110 ms after the release (160 ms after the first press) is a repeat of the letter on QMK and a 200 ms hold of Option on kanata (Option down at 360). A re-press that QMK treats as a repeat can therefore be a hold on kanata by as much as the first tap lasted. No setting makes the two agree for every tap length. `translateHoldTapProfile` now says so in a note whenever `QUICK_TAP_TERM` is set (the default, which equals the tapping term, gets no note), and the translation table has the row.
2. **A tap is released later when the next key is also a hold-tap.** S down, J down 30 ms later, S up at 80, J up at 110: QMK releases S at 80 and types J at 110; kanata presses S at 80 and keeps it down until 116, 6 ms after J is down. The letters typed are the same (`s`, `j`). It happens with every variant that resolves S as a tap, so it is kanata's, not an option's. With `HOLD_ON_OTHER_KEY_PRESS` both give Option+J, at the same time.

Nothing else differs: the hold decisions agree on the same event and the same millisecond (within the 6 ms lag), for the tapping term, `PERMISSIVE_HOLD`, `HOLD_ON_OTHER_KEY_PRESS`, `CHORDAL_HOLD` with either of them, and `FLOW_TAP_TERM` against `require-prior-idle-ms`, including tapping-term timeouts and the "hold past the term with another key down" cases.

## The translation bug

Before this spike `CHORDAL_HOLD` alone was translated to `tap-hold-opposite-hand`. They are not the same: kanata's variant resolves to a hold the moment an opposite-hand key goes down, which is QMK's `CHORDAL_HOLD` plus `HOLD_ON_OTHER_KEY_PRESS`. QMK with chordal hold alone decides nothing on an opposite-hand press; the key is a tap if it is let go before the term, whatever was pressed on the other hand. In the simulator, with S down and U tapped inside it, QMK typed `S U` and kanata Option+U, which is a modifier on a fast cross-hand roll, the misfire home-row mods are meant to prevent. Six of the fifteen scenarios disagreed with `CHORDAL_HOLD` alone.

The fix is in `src/layout/kanata/profiles.ts` and `src/firmware/kanata/generate.ts`:

| QMK | kanata |
|---|---|
| `CHORDAL_HOLD` | `tap-hold-tap-keys` over the key's own hand (new profile option `tap-keys: same-hand`; the generator writes `left-keys` and `right-keys` and uses the one the key is on) |
| `CHORDAL_HOLD` + `HOLD_ON_OTHER_KEY_PRESS` | `tap-hold-opposite-hand` (was already that, by accident; now by rule) |
| `CHORDAL_HOLD` + `PERMISSIVE_HOLD` | `tap-hold-opposite-hand-release` (unchanged; verified) |

A same-hand profile on a key the board gives no hand is refused rather than written as something else. After the fix every chordal scenario matches. Tests: `test/layout/kanata-hold-tap.test.ts` (the three rows, the option, the note, the generated file, `kanata --check`, the refusal) and `test/firmware/kanata/sim.test.ts`.

The other (S6) rows are now confirmed against the simulator: `PERMISSIVE_HOLD` to `tap-hold-release`, `HOLD_ON_OTHER_KEY_PRESS` to `tap-hold-press`, `CHORDAL_HOLD` with permissive to `tap-hold-opposite-hand-release`, and `FLOW_TAP_TERM` to `require-prior-idle-ms`. The ZMK rows were not exercised (no ZMK emulation here); `tap-preferred` to `tap-hold-tap-keys` is in effect BK's own rule, below.

## BK's own MacBook profile

BK's layout (from a read-only `.backup` of `~/.local/share/keyloom/keyloom.db` in a scratch directory) has `home-row-300`: `tap-hold-tap-keys`, 300 ms, over every key, on S, F, G, H, J, L, Z and `/`, and the Space layer as `tap-hold-press` at 1000 ms. There is no QMK option with those semantics, so this one has no QMK side. Through the simulator, with the generated file: any other key pressed while S is down makes S a tap, even a key still down well into the hold (U down at 100 ms came out as `S` at 101 ms and `U` at 107 ms); a lone S held is Option from 298 ms. That is the "roll equals tap" rule of D-242, as designed.

## Repeating it

Needs the built binary (above); no Docker.

```
KEYLOOM_KANATA_SIM=~/.cache/keyloom-s33/target/release/kanata_simulated_input bun test test/firmware/kanata/sim.test.ts
```

It runs all 150 pairs against the recorded QMK reports in `test/fixtures/kanata-sim/qmk.json`, and fails if a pair's verdict is not `match` or is not the listed known difference. Without the variable the file's gated tests skip. To re-record the QMK side (Docker and the pinned checkout, 10 emulator runs):

```
agent-work run -- bun scripts/record-hrm-qmk.ts
```

Not covered: ZMK's behaviour, `RETRO_TAPPING` and the rest of the options with no kanata form (reported, not carried), a held key's auto-repeat, layer-tap holds, and how any of it feels under real fingers.
