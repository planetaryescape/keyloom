# S43: do derived boards build from the pinned trees?

## What was run

2026-10-17, rung 21 part 2, on `origin/main` at `25db61c` plus this change, on BK's Mac (Docker 29.6.2 on Colima, arm64). Each board was written with `keyloom keyboard add --candidate <id> --home-row 2` into a scratch data directory, a blank config was made with `keyloom keyboard put <glove80 layout> --on <board>`, and `keyloom build <config>` ran through `agent-work run --`. The head of each config was its blank layout, so the build is the firmware default keymap that keyloom generates, with none of BK's proposals applied. Nothing was flashed.

Pins (`src/boards/derive/pins.ts`): qmk_firmware `7a1bbf37c5c07da4ea0a162bb139083a46ef40a1`, zmk `4dd95d7840eb3d5a3f59bb29fbf1ab054715ef85`, images `ghcr.io/qmk/qmk_cli@sha256:b7d7fa8f…` and `zmkfirmware/zmk-build-arm@sha256:edb1c953…`.

## What failed and the fix

The first Ferris build stopped at `.build/obj_ferris_0_2_base_keyloom/protocol/chibios/usb_driver.o`:

```
tmk_core/protocol/chibios/lufa_utils/LUFA/Drivers/USB/USB.h:37:10: fatal error: lib/lufa/LUFA/Drivers/USB/Class/Common/HIDClassCommon.h: No such file or directory
```

QMK's ChibiOS USB code includes LUFA's headers, so a ChibiOS board needs `lib/lufa` as well (S5 hit the same error through ZSA's Oryx module, and had it in the Moonlander's list). `qmkSubmodules` in `src/boards/derive/build-board.ts` now adds `lib/lufa` to the ChibiOS and RP2040 lists. After re-adding the board with `--force` and rebuilding, it built. The RP2040 board was built only with `lib/lufa`; a build without it was not tried.

## What held without a change

- The AVR list (`lib/lufa` alone) built `planck/rev4` and `crkbd/rev1`.
- The ZMK block as the generator writes it: `board: "nice_nano//zmk"`, `physicalLayout: "app/dts/layouts/foostan/corne/6column.dtsi#foostan_corne_6col_layout"`, targets `corne_left` and `corne_right`. West printed `Board: nice_nano, Revision: 2.0.0, qualifiers: nrf52840/zmk` and `Shield(s): corne_left`, and found `corne_left.overlay` and `boards/nice_nano_nrf52840_zmk.overlay` in the pinned tree.
- keyloom's own Corne is a different build (ZMK `edf5c08`, `nice_nano_v2`); this one shows the pinned ZMK main builds with the v2 names.

## What this does not show

Nothing was flashed and the firmware was not run, so none of these images is known to type. The flash recipes for these bootloaders (D-365) are tested against fake tools only. The smoke build used the pinned QMK mainline tree, so it says nothing about vendor forks.
