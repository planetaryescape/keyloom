### Tool execution and result meaning

The common wrapper is usable: `src/agent/run-turn.ts:67-83,123-146` wraps tools before handing them to `AgentModel`. Anthropic/OpenRouter adapt `run` directly (`src/agent/anthropic-model.ts:31-45,67-96`); Codex wraps it for its limit, then invokes it through MCP (`src/agent/codex-model.ts:75-103`, `src/agent/codex/tool-server.ts:38-46,67-98`). There is no separate OpenRouter adapter file: the attempted read of `src/agent/openrouter-model.ts` failed because OpenRouter shares `anthropic-model.ts`.

However, `ok` means "the JavaScript function returned", not "the requested operation succeeded". The proposal handler returns `INVALID` text normally and records validation failures separately (`src/agent/tools/propose-changes.ts:28-54`, `src/agent/recorder.ts:5-14`). Invalid input throws from `defineTool` (`src/agent/tools/define.ts:19-26`). A rejected proposal therefore must not render as a successful validation step merely because the wrapper returned. Mixed valid/invalid alternatives also need per-alternative results, rather than one undifferentiated green check; this last requirement follows from the handler's loop, not a mixed-alternative experiment here.

The current callback supplies only a name, with no result or invocation ID (`src/agent/run-turn.ts:23-29`, `src/api/http.ts:309-320`). Allocate a local operation identity at wrapper entry, preserve it through completion/failure, and attach typed validation information to that invocation. The aggregate recorder's tool-name list is insufficient for correlating repeated or parallel calls. Do not recover success by parsing model prose or matching the last same-named call.

Codex's fixture emits a failed `status` for an MCP error but can omit the separate `error` field (`test/helpers/fake-codex.ts:61-69`). The parser retains `status`, but `synthesise` sets `is_error` only from `call.error` (`src/agent/codex/events.ts:6-15`, `src/agent/codex-model.ts:42-58`). The probe observes an error string without its neutral error flag. This is a concrete supported-fixture replay gap; whether the installed live Codex binary emits exactly that shape was not tested. Use the in-process wrapper as the primary activity failure source and add status-only adapter coverage during implementation.

### Public notes, final answers and thinking

`ContentBlock` separates neutral text/tool blocks from opaque provider replay (`src/agent/model.ts:7-18`), but `ModelRequest.onText` has no message identity, boundary or public-note/final role (`49-58`). Both adapter paths can observe more than that callback exposes:

- Anthropic/OpenRouter await each SDK `finalMessage`, including its full content and stop reason (`src/agent/anthropic-model.ts:105-125`). The fixture's text is delivered in chunks before that boundary. A provider-neutral observer could publish a completed public message there without exposing opaque blocks. This is a feasible seam inferred from source and the scripted run, not a new implemented callback.
- Codex receives completed `agent_message` items with IDs and whole text, but drops the IDs when constructing `steps`; it adds blank lines when forwarding `onText` (`src/agent/codex/events.ts:17,47-55`, `src/agent/codex-model.ts:166-195`). No public channel/final-role field survives this parser. Treat text before later tools as working notes and the terminal public response as the answer; do not claim a provider-native role distinction that is absent here.

The live/reloaded mismatch is observed, not hypothetical (`test/spikes/S54.test.ts:105-118`):

```text
Anthropic/OpenRouter live: ["Checking.Finished."]
Codex live:               ["Checking.\n\nFinished."]
All three loaded:         ["Checking.", "Finished."]
All three terminal text:  "Finished."
```

The reducer appends every delta into one turn and retains that text on `done`; reload reconstructs separate messages (`src/web/chat/transcript.ts:64-87,159-183`). It cannot classify notes correctly from today's stream. Keep a streamed message provisional until a safe boundary; reclassify after subsequent tool activity. If safe incremental observation is unavailable, show the completed public message whole. Show a generic waiting/thinking state while the model is running, never opaque thinking text or fabricated progress.

### Questions and cancellation

Anthropic/OpenRouter detect `ask_user` before executing any tools in that reply. They persist its pending call and mark sibling calls not run (`src/agent/anthropic-model.ts:120-137`). This means wrapper-only instrumentation cannot observe their question call. Codex actually executes the pausing tool through MCP, then stops on the completed call (`src/agent/codex-model.ts:81-99,189-197,226-234`). Its question handler only returns a fixed message (`src/agent/tools/ask-user.ts:16-24`). Observe waiting at the model's pending-question boundary; do not invent an executed tool event on the Anthropic paths.

The application checks an answer against the exact open call before storing it, and reconstructs the question from stored blocks (`src/app/conversations.ts:106-113,181-190,284-301`). The harness observes reload and duplicate-answer refusal for every path. Existing Anthropic tests additionally check sibling calls are skipped (`test/agent/ask-user.test.ts:80-93`). No hours-long model process is retained while waiting.

The response body's cancellation aborts backend execution in the direct route probe (`test/spikes/S54.test.ts:143-163`). Source also couples request abortion to the same controller (`src/server/chat-routes.ts:118-125`). The Codex adapter kills the child and raises `AbortError` (`src/agent/codex-model.ts:135-145,213-224`). Anthropic/OpenRouter pass the signal into the SDK (`src/agent/anthropic-model.ts:96`). These tests cancel after a real synthetic config commits, not before execution starts.

The tool interface itself accepts no signal (`src/agent/model.ts:20-34`), and the common wrapper does not check one. Cancellation is not rollback and cannot prove that an already-entered operation stopped. The harness does not test an in-flight external job; no build or flash was started.

### Reconnect verdict

Current code does not meet durable reconnect:

1. A config is committed through `createAgentPorts.newConfig` and `newConfig` before model history is stored (`src/app/agent-ports.ts:63-67`, `src/app/configs.ts:101-129`, `src/app/conversations.ts:225`). The cancellation experiment leaves the config but only the user message. A later explicit resend executes `create_config` again. Name uniqueness prevents a second same-named config; it does not return the original successful effect receipt.
2. The busy lock is an in-memory set (`src/app/conversations.ts:100-101,173-176,252-254`). It is not restart recovery or client-request deduplication.
3. The SSE frames have no sequence/event ID (`src/server/chat-routes.ts:51`); the route has no catch-up cursor. The reducer appends text without duplicate-delivery identity (`src/web/chat/transcript.ts:64-71`). Exact durable event replay was not runnable because no stored-run/event implementation exists at this SHA.

Reading an existing conversation does not itself call the model. The unsafe substitute for recovery is resending a POST. Do not auto-resend on reconnect. None of this experiment observed an actual duplicate config: the demonstrated failure is a lost receipt and repeated attempt, with a name-conflict result instead of idempotent recovery.

## Proposed bounds and migration compatibility

These are bounded implementation recommendations, not measured storage requirements or a frozen schema:

| Item | Proposed bound |
|---|---|
| Serialized presentation event, including envelope | 4 KiB UTF-8 |
| Operation label/result summary | 512 bytes each, UTF-8 safe truncation |
| Allowlisted input/output detail | 512 bytes input; 1 KiB output; omit raw result by default |
| Per-run presentation events | 256 events and 256 KiB total, whichever comes first |
| Actual tool executions per run | 64; independent of a provider's iteration count |
| Reserved terminal/snapshot budget | 64 KiB within that 256 KiB total |

Do not persist every token delta. Store completed public messages once in the existing message store and reference them from presentation records. Artifact payloads should reference existing proposals/configs/revisions rather than copy layout dumps; any new inline artifact payload needs its own explicit cap before that kind ships. The proposed presentation budget does not pretend to bound legacy model replay or all domain data.

Use server-owned labels, result counts, validation codes and stable references. Unknown tools get name/state/duration only. Do not store raw inputs, raw exceptions, provider replay, credentials, passages, trace data or full tool returns in activity details. A free-text name or priority may itself contain private text: don't assume a generic string scrubber makes it safe. Test allowlists with synthetic secret/recording canaries; this spike did not implement or verify a sanitizer.

Reserve terminal capacity before admitting another operation; stop future execution visibly at the limit rather than silently losing starts, failures or effect references. Coalesce transient phase chatter. Do not prune active/waiting runs or effect receipts for a detail budget. Keep completed bounded summaries for the conversation lifetime, delete presentation records with the owning conversation, and retain domain records under their existing ownership. If later pruning is added, preserve a terminal snapshot and earliest available sequence so a cursor receives a snapshot instead of a fabricated gap-free replay.

Migrate additively. Keep existing message/change-set IDs, layout ownership and provider-specific replay intact. Don't backfill fake tool outcomes from old name lists. Old conversations show "Working details unavailable for this older conversation". Keep the existing chat route and wire shape for old clients; expose new observation through negotiated/versioned capability or a successor route. Adding new discriminated event types to the old stream can break strict old parsers. Unknown protocol major versions refuse writes; optional presentation additions need a fallback. Workspace/cross-board ownership remains S55, outside this spike.

## Recommend a releasable 26a, then 26b

26a: **honest visible work for today's layout-scoped conversation**. Reuse `AgentModel`, `AgentPorts`, `runAgentTurn`, existing questions/proposals and the pure reducer. Ship real correlated tool start/result/failure, semantic validation refusal, public message boundaries, clear user/agent roles, restrained thinking and a successful completed-work disclosure that can reopen. Store bounded completed presentation alongside existing history; show the legacy fallback where absent. Keep questions, failures and unapplied proposals visible. Verify the same inspection through CLI, served-app screenshots and installed candidate before release. This spike did not perform those product checks.

26a must say what it cannot do: connection loss still ends socket-owned execution; Stop does not undo already prepared configs/proposals; interrupted activity can be incomplete. Reconnect only reads stored state, never re-POSTs. Show "Connection lost/stopped; some preparation may already have completed. Inspect configs and proposals before retrying." Do not label 26a "durable runs", promise continuation of active work after reload, or mark full rung 26 built. If preserving execution across panel closure is a non-negotiable first-release criterion, 26a alone is insufficient.

26b: **reload the same running work without rerunning effects**. Separate execution from subscribers, persist run identity/request deduplication and event cursor, record local effect plus receipt in the same transaction, reconcile linked job IDs, retain explicit Stop and recover server restarts as interrupted. Exercise disconnect after commit, duplicate POST/answer/cancel, duplicate/out-of-order event delivery and a process restart. Existing tools that mutate proposals, memory or configs all need the receipt audit; protecting only `create_config` does not establish the guarantee. Keep new workspace targeting and app-wide capability expansion out until this vertical journey is released.

Do not let later rungs bind to an undeployed 26a/26b schema. Settle the smallest wire contract together with its provider, persistence, CLI and UI implementation; use this report as evidence, not as an exportable API specification.

### Knowledge packet for the implementation owner

- Instrument the common wrapped `run`, but observe `ask_user` pending state separately because two providers intentionally bypass its handler.
- Separate transport success from domain success; a normally returned rejected validation is not a successful operation.
- Add safe public message boundaries; `onText` alone merges working notes into the final answer and changes shape on reload.
- Take error truth from the wrapper, not exclusively Codex's synthesized replay flag.
- Never equate an aborted stream with a rolled-back effect. The receipt/history gap is reproduced on all three providers.
- Release 26a only with explicit non-durable limitations, or include 26b before claiming the full reconnect promise.
